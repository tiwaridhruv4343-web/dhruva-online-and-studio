# DHRUVA ONLINE AND STUDIO AND STUDIO — Online-Service Portal

This is an upgrade of the existing DHRUVA ONLINE AND STUDIO AND STUDIO website. The original branding, landing page and configuration approach are preserved, while a real backend portal structure has been added.

## Stack
- Frontend: existing HTML/CSS/JavaScript website + portal pages
- Backend: Node.js + Express
- Database: SQLite (`better-sqlite3`)
- Password hashing: `bcryptjs`
- Private document upload: `multer` with random server-side filenames
- Authentication: HTTP-only session cookie + server-side sessions
- No paid API is required for the core portal.

## Run locally
Requirements: Node.js 18+.

```bash
npm install
npm start
```

Then open `http://localhost:3000`.

Do NOT open `portal.html` directly as a file; the backend must be running for authentication, applications and uploads.

## Pages
- `/index.html` — existing public website
- `/auth.html` — registration/login/forgot-password UI
- `/portal.html` — authenticated user dashboard
- `/track.html` — application tracking
- `/admin.html` — protected admin console

## Admin security
There is intentionally NO hard-coded default admin password.

To create the first admin securely, run the one-time script:

```bash
node server/create-admin.js
```

It prompts for an email, name, mobile and password and stores only a bcrypt password hash.

After creation, use `/auth.html` to sign in. Admin access is based on the database role.

## Documents
Accepted: PDF, JPG, JPEG, PNG.
- Maximum 5 files per application
- Maximum 5 MB per file
- Uploaded files are stored outside the public web directory with random filenames.
- Admin document metadata and authenticated inline viewing are provided through protected routes; uploads are never served as a public static directory.

## Password reset
The UI and backend endpoint are present. Actual email delivery requires SMTP credentials to be supplied in deployment environment variables. The endpoint deliberately does not reveal whether an email exists.

## Payments
Payment is NOT falsely marked as working. The portal displays a payment-ready state and isolates future gateway configuration. Do not collect or store card/UPI credentials in this application. Add a server-side payment provider SDK/webhook flow later.

## WhatsApp
The existing `js/config.js` remains the single place for the public WhatsApp number used by the website. The portal also uses the same configuration when applicable.

## Free deployment
The application can be deployed on a free/low-cost Node-compatible host where available. SQLite is appropriate for development and small deployments, but check the host's persistent-disk policy before production use. For larger production workloads, move the database and private file storage to managed infrastructure.

## Important production hardening
Before accepting real customer documents:
1. Use HTTPS.
2. Set `NODE_ENV=production`.
3. Use a strong random `SESSION_SECRET`.
4. Configure backups and persistent storage.
5. Add CSRF protection, rate limiting, audit logging and malware scanning for uploads.
6. Implement authenticated document streaming/download with per-user authorization.
7. Configure SMTP for password resets.
8. Add a real payment provider only when needed.
9. Do not expose the SQLite database or upload directory through a public web server.


## Free cloud deployment: Render

This repository is prepared for a Render **Web Service** because the project contains both
browser frontend files and a Node.js/Express backend.

- Build command: `npm install`
- Start command: `npm start`
- Health check: `/health`
- Node runtime: 20.x
- Required runtime setting: `NODE_ENV=production`
- `SESSION_SECRET` is generated by the included `render.yaml`.
- Do **not** set `PORT` manually; Render supplies `PORT` to the process.
- CORS is not required for the current architecture because the frontend and API are served
  from the same origin by `server/server.js`.
- Render provides a public HTTPS `onrender.com` URL after deployment.

### Important free-plan storage limitation

The current application intentionally uses SQLite and private local uploads. Render's free
web-service filesystem is ephemeral: SQLite data and uploaded documents can be lost when the
free service restarts, spins down, or redeploys. Render documents this limitation. Therefore
the free Render deployment is suitable for preview/testing of this exact project, but it is
not a safe long-term production datastore for real customer applications/documents.

For a durable production launch, the database should be moved to persistent/managed storage
and uploaded documents to persistent object/file storage. That requires a separate storage
architecture and should not be represented as working on the free filesystem.
